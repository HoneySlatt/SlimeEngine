# 0164. Play

- Status: Accepted
- Date: 2026-10-28

## Context

[ADR-0155](0155-the-editors-design.md) decided Play (its decision D5): the editor starts the
game's program as [ADR-0110](0110-how-the-editor-runs-a-games-code.md) says, through
`slime_channel::launch`, with a token and a save of the editor's own, and hands it the scenes that
hold steps not written as private copies, through an option of development builds that the engine
handles once for every game, the user's files left alone; Play, Pause, Step, Speed and Stop in a
toolbar; a console of the game's log. Milestone M6c.4 was cut in three at its start, on
2026-10-28, as ADR-0155 allows: M6c.4a, Play itself, which this ADR records; M6c.4b, the edits
made while the game runs and agents driving both programs; M6c.4c, the game built again and Play
measured. How the scenes are handed over was the owner's to choose, the same day, among three
ways: files of a directory that an environment variable names, read by the engine; a function
that each game calls; the texts sent over the development channel before the game loads.

What the code held before this milestone:

- `slime_channel::launch` starts a program with a token in its environment, a pipe as its standard
  input, which ends it once closed, and waits for it to say where it listens
  ([ADR-0122](0122-the-development-channel.md)); a `Client` asks it what the channel offers, its
  time paused, stepped, at a speed, its log read, its stop.
- Every game makes its library of scenes with `SceneLibrary::of`, from its cooked data, before
  its run starts or as it starts; a scene inserted by hand stands for the cooked one of the same
  ID.
- The editor's program ran no game.

## Decision

**The scenes are handed over as files of Play's own directory.** With the `development` feature,
which `slime-app`'s turns on, `slime-world`'s `SceneLibrary::of` inserts the scene files of the
directory that the environment variable `SLIME_PLAY_SCENES` names, each named after its asset ID,
`<id>.scene`, in place of their cooked files. Play makes a new directory of its own, of a name
that no other program could guess, in the system's directory of temporary files, writes there the
text of the level's scene file as writing it would give, whether or not its file holds every step,
since the cooked data may be older than the file, and names it to the game; the save of the
editor's own lies there too. The user's files, sources and cooked data, are left as they were; the
directory is removed once the game ended, or as the editor quits.

**A game program is the editor program's to give.** `Program::play` builds the command that
starts the game, built already, from what Play hands it (`Played`): the cooked data, Play's save,
and whether the editor runs without a window, as agents run it, the game then running without one
where it can. `Played::program` finds a program beside the editor's own, where cargo builds a
workspace's programs: *Hunna Wood*'s editor plays `hunnawood` on a new run, and the `editor`
example plays the yard in the `world` example.

**Threads of Play's own drive the game.** `play.start` writes Play's directory, then a thread
starts the game through `slime_channel::launch_unless`, which gives the start up once Stop is
asked, and drives it through a `Client`: it sends the controls that the editor asks, asks the game
how game time stands after each, which the toolbar shows, and looks whether the game ended.
Another thread reads the game's standard error, its log, to its end, a panic's message and the
last lines of a stop included; each thing that they tell wakes the editor's loop. A game slow to
answer, hung or crashed never holds the editor's window. Stop asks the game to stop, and a watch of
its own kills it ten seconds later if it has not, whatever the thread that drives it waits on; an
editor that quits kills the game that it plays, and one that crashes leaves no game behind either,
the game's standard input, which Play holds, closing with it; a game that ends by itself, crashed
or not, is told to the user, with how it ended, and the editor goes on.

**The toolbar, the console and the operations.** Above the viewports, a toolbar holds *Play*,
*Pause* or *Resume*, *Step*, which pauses and runs one fixed step, *Stop*, and the speeds of game
time, ¼, ½, 1 and 2, four segments, the one in use chosen; the *Play* menu holds Play, Pause, Step
and Stop, F5 plays, Shift+F5 stops, F7 pauses and F8 steps. They are operations that agents run
by name, `play.start`, `play.pause`, `play.step`, `play.speed` with a speed, and `play.stop`, of the
kind `play`. Once
Play ran, a console below the viewports shows the last 500 lines of the game's log, the last in
sight, which the editor's own log writes too, under the target `game`, with each start, refusal and
end of Play: an agent reads them there.

## Alternatives considered

- **A function that each game calls** after making its library: `slime-world` would read no
  environment, but a game that forgets the call plays the files on disk, where ADR-0155 asks that
  the engine handle it once for every game.
- **The texts sent over the development channel** before the game loads: no file, but every game
  would wait for the editor before loading anything, and the channel would gain the order of a
  start.
- **The level written over its own file, then cooked, the game run with `--watch`**: ADR-0155
  rejected it, the user's files written by Play.
- **The game driven from the editor's own thread**: a game that hangs would hang the editor's
  window, which every request would wait on.
- **The log read over the development channel**: a game that hangs would hold the reading, and the
  lines that a game writes as it stops or crashes, after its channel closed, would be lost.
- **The game killed by the thread that drives it**: that thread may wait on a request that a hung
  game never answers; the kill is a watch of its own.
- **The console in a floating panel**: a panel that the user opens and loses; below the viewports,
  the log is where the game is watched.

## Consequences

- Every game that makes its library through `SceneLibrary::of` plays what an editor hands it, in a
  development build; a build for shipping reads no such directory.
- A game that makes its library before `slime_app::run` starts its log, as *Hunna Wood* and the
  `world` example do, does not log the scenes that Play gave, nor a file of Play's directory that
  it left out.
- Play starts a program built already: M6c.4c builds it again when its code changed.
- The steps made while the game runs are not sent to it yet: M6c.4b sends them, and lets agents
  drive the game itself.
